# 깃 브랜치 전략

이 문서는 `smng-poe-pricer` 백엔드 프로젝트의 브랜치 운영 방식과 개발 워크플로우를 정의한다.
브랜치 모델은 Simplified Git Flow를 사용하며, 태그 규칙 상세는 [배포-태그-버전-규칙.md](배포-태그-버전-규칙.md)를 따른다.

> **⚠️ 2026-06 개정**: BE는 `pricer-v*`(독립 네임스페이스), FE는 `poe-economy-v*`. 과거 "동일 `poe-economy-v*` 공유"는 폐지. 조합은 배포 매니페스트가 기록. 상세 [깃-전략.md §2](깃-전략.md). 아래 본문의 `poe-economy-v…` 예시는 BE에서 `pricer-v…`로 동일 형식 적용.

## 1. 브랜치 모델

```text
main    ───────────────────────── poe-economy-v2.15.0 ──→
                                      ↑
develop ── dev.1 ── dev.2 ───────────┘ ── dev.N ───────→
              ↑
feature/X ────┘
```

| 브랜치 | 역할 | 직접 push | 병합 대상 | 태그 |
|--------|------|----------|----------|------|
| `main` | 프로덕션 릴리즈 지점 | 금지. 릴리즈 절차에서만 push | 없음 | 릴리즈 태그만 (`pricer-vA.B.C`) |
| `develop` | 개발 통합, 스테이징 배포 기준 | 허용 | `main` | dev 태그만 (`pricer-vA.B.C-dev.N`) |
| `feature/*` | 개별 기능 개발 | 허용 | `develop` | 없음 |
| `bugfix/*` | 개발 중 버그 수정 | 허용 | `develop` | 없음 |
| `hotfix/*` | 프로덕션 긴급 수정 | 허용 | `main` + `develop` | 없음 |
| `wip/*` | 실험 또는 미완성 작업 | 허용 | 없음 | 없음 |

핵심 원칙은 다음과 같다.

- 일반 기능은 반드시 `develop`에 먼저 반영한다.
- `main`은 릴리즈 또는 hotfix 목적 외에는 직접 작업하지 않는다.
- 릴리즈 시에는 `develop -> main` fast-forward 병합을 기본으로 한다.
- hotfix는 `main`에서 분기하되, 완료 후 반드시 `develop`에도 병합한다.

## 2. 일상 개발 워크플로우

### 2.1 기능 개발

```powershell
git checkout develop
git pull origin develop
git checkout -b feature/trade2-normal-base
```

작업 완료 후:

```powershell
git add <changed-files>
git commit -m "feat: Trade2 일반 베이스 수집 추가"
git push origin feature/trade2-normal-base
```

`develop` 반영:

```powershell
git checkout develop
git pull origin develop
git merge --no-ff feature/trade2-normal-base
git push origin develop
git branch -d feature/trade2-normal-base
```

작업 규모가 작고 충돌 가능성이 낮으면 `develop`에서 직접 커밋할 수 있다. 다만 운영 영향이 있거나 리뷰가 필요한 변경은 `feature/*` 브랜치로 분리한다.

### 2.2 명명 규칙

| 용도 | 패턴 | 예시 |
|------|------|------|
| 기능 | `feature/<name>` | `feature/trade2-normal-base` |
| 버그 수정 | `bugfix/<name>` | `bugfix/latest-price-carry-forward` |
| 리팩토링 | `refactor/<name>` | `refactor/price-summary-math` |
| 문서 | `docs/<name>` | `docs/branch-strategy` |
| 실험 | `wip/<name>` | `wip/market-discovery-quota` |
| 긴급 수정 | `hotfix/<name>` | `hotfix/prod-scheduler-crash` |

## 3. Dev 태그와 스테이징 배포

dev 태그는 `develop` 브랜치에서만 생성한다.

```powershell
git checkout develop
git pull origin develop
node scripts/check-tag-consistency.js
node scripts/create-dev-tag.js
git push origin develop --follow-tags
```

릴리즈 직후 첫 dev 태그는 타겟 버전을 명시한다.

```powershell
node scripts/create-dev-tag.js --target v2.16.0
```

미리보기:

```powershell
node scripts/create-dev-tag.js --dry-run
```

## 4. 릴리즈 절차

릴리즈는 `develop`에 통합된 내용을 `main`으로 fast-forward한 뒤 릴리즈 태그를 생성한다.

### 4.1 사전 검사

```powershell
node scripts/check-tag-consistency.js
git status
git log --oneline develop..main
git log --oneline main..develop
```

`develop..main`에 출력이 있으면 `main`에만 있는 커밋이 있다는 뜻이다. 이 경우 릴리즈를 진행하기 전에 원인을 확인한다.

### 4.2 릴리즈 수행

```powershell
git checkout main
git pull origin main
git merge --ff-only develop
git tag poe-economy-v2.16.0
git push origin main
git push origin poe-economy-v2.16.0
```

릴리즈 후 `develop` 동기화:

```powershell
git checkout develop
git merge --ff-only main
git push origin develop
```

## 5. Hotfix 절차

프로덕션 긴급 수정은 `main`에서 분기한다.

```powershell
git checkout main
git pull origin main
git checkout -b hotfix/prod-scheduler-crash
```

수정 후 `main` 반영:

```powershell
git add <changed-files>
git commit -m "fix: 프로덕션 스케줄러 크래시 수정"
git checkout main
git merge --no-ff hotfix/prod-scheduler-crash
git tag poe-economy-v2.16.1
git push origin main
git push origin poe-economy-v2.16.1
```

`develop`에도 반드시 반영:

```powershell
git checkout develop
git pull origin develop
git merge --no-ff hotfix/prod-scheduler-crash
git push origin develop
git branch -d hotfix/prod-scheduler-crash
```

## 6. Pre-commit Hook

레포 최초 clone 후 1회 설치한다.

```powershell
Copy-Item .hooks/pre-commit .git/hooks/pre-commit
```

Git Bash 환경:

```bash
cp .hooks/pre-commit .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

hook은 커밋 시 `node scripts/check-tag-consistency.js`를 실행해 dev 태그 타겟 혼용을 차단한다. hook 우회는 금지한다.

## 7. 트러블슈팅

### 7.1 실수로 main에 직접 커밋하거나 push한 경우

아직 push하지 않았다면 커밋을 feature 브랜치로 옮긴다.

```powershell
git branch feature/recover-main-work
git reset --soft HEAD~1
git checkout feature/recover-main-work
git commit -m "feat: ..."
```

이미 push했다면 임의로 force push하지 않는다. 먼저 변경 내용이 `develop`에 반영되어 있는지 확인한다.

```powershell
git log --oneline main..develop
git log --oneline develop..main
```

그 다음 `main` 정리는 팀 또는 사용자와 합의한 방식으로 처리한다. 선택지는 revert, 릴리즈 merge로 흡수, 또는 명시 승인된 히스토리 정리다.

### 7.2 develop이 main보다 앞서 있는 경우

정상적인 개발 상태다.

```powershell
git log --oneline main..develop
```

릴리즈 준비가 끝나면 사전 검사 후 `develop -> main` fast-forward를 진행한다.

### 7.3 main이 develop보다 앞서 있는 경우

hotfix가 `develop`에 반영되지 않았거나, main에 직접 커밋이 들어간 상태일 수 있다.

```powershell
git log --oneline develop..main
```

hotfix라면 `develop`에 병합한다. 실수로 들어간 커밋이면 `develop` 반영 여부와 main 정리 방식을 먼저 결정한다.
